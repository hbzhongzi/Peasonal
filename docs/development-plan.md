## 2. 阶段划分原则

1. **每个阶段结束都必须是一个「可运行、可验证」的状态**，不存在"做到一半跑不起来"的中间态。
2. **先打通一条完整路径，再横向扩展**。M1 只做公开读路径（不含后台），先把"访客看到文章"这件事跑通，再在 M2 做写路径。
3. **能力按「依赖」而非「重要性」排序**。SEO（M4）排在后台（M2）之后，是因为爬虫注入需要依赖文章的渲染结果稳定下来。
4. **不为"将来可能"的需求预留抽象**。需要时再抽，改动成本远低于提前设计的维护成本。

## 3. 开发工作流（每个阶段通用）

### 3.1 分支与提交

```
main            # 始终保持可运行
└── dev/m1      # 阶段分支，完成后合并回 main
```

- 提交格式：`<type>(<scope>): <描述>`，type 取 `feat` / `fix` / `refactor` / `docs` / `chore`
- 一个阶段一个分支，避免长期分支漂移

### 3.2 每阶段的标准动作

1. 从 `main` 切 `dev/mx`
2. 按本文任务清单推进，完成后**本地验证**
3. 跑通验证命令（见各阶段的「验证方式」小节，如 M1 §4.6、M2 §5.5）
4. 更新文档（见 §8 文档维护规范 —— **硬性要求**）
5. 合并回 `main`

### 3.3 数据库变更纪律

> 来源：技术方案 §1.2.2。这三条是硬约束，违反会导致 schema 与迁移版本号对不上。

1. **一个迁移文件只放一条 DDL**，文件头带 `-- +goose NO TRANSACTION`
2. **每个文件的 `down` 必须实测过**，不能只写不验
3. 改完 `queries/*.sql` 后**必须跑 `make sqlc`** 重新生成，不要手改 `*.sql.go`

### 4.4 涉及的表

`posts`、`tags`、`post_tags`。

**本阶段新增了 7 个迁移**：

| 迁移 | 内容 | 理由 |
| --- | --- | --- |
| `00013_add_posts_toc.sql` | `posts.toc_json TEXT` | TOC 必须和 `content_html` 一起落库：实时解析等于每次请求跑一遍 DOM 解析，而两者同属一次渲染产物，一起写库才能保证永不脱节。用 `TEXT` 而非 `JSON`，因为 sqlc 对 MySQL JSON 列的类型推断不稳定，且 TOC 只有几 KB |
| `00014`–`00018` | 5 张表的审计字段补 `DEFAULT CURRENT_TIMESTAMP(3)`（`updated_at` 另加 `ON UPDATE`） | 所有表原本都是 `DATETIME(3) NOT NULL` **无默认值**，MySQL 严格模式下任何 INSERT 少传一个就报 Error 1364。这不是某条 SQL 写漏，而是 schema 没兜底。追加 ALTER 而非改 `00001`，是因为已执行的迁移不可改写 |
| `00019_drop_tags_post_count.sql` | 删除 `tags.post_count` | 该列从未被任何代码写入，永远是 0；实际计数由 `ListTagsWithCount` 用 JOIN 实时算。留着它最危险的地方是「看起来是对的」，将来谁直接读它会拿到 0 而不起疑 |

### 5.3 安全要点（对应技术方案 §5.5）

> 这三条写在这里是因为它们**必须在写代码时就成立**，事后补会很别扭：

1. **读公开、写受限**：`/uploads/*` 任何人可读（否则前台图片全挂），上传/删除必须管理员
2. **文件名一律服务端生成** `<ULID>.webp` —— 一次性解决路径穿越、中文名、同名覆盖
3. **登录用户也要限流**（20 次/分钟）—— 鉴权不等于防滥用

### 5.4 验收标准

- [ ] 浏览器走完：登录 → 新建 → 传图 → 发布 → 前台可见 → 下线
- [ ] 刷新页面后登录态保持（靠 HttpOnly Cookie 里的 refresh token）
- [ ] access token **不在** localStorage / sessionStorage 中
- [ ] 上传 5MB 以上的文件返回 413，且**服务端没有把文件读进内存**
- [ ] 上传 `.svg` 被拒绝；把 `.php` 改名成 `.png` 上传被拒绝（读文件头识破）
- [ ] 未登录调 `/admin/*` 返回 401

curl -X POST localhost:8080/api/v1/admin/posts     # 无 token → 401
curl -X POST localhost:8080/api/v1/admin/login -d '{...}'   # 拿 token

## 9. 文档维护规范（硬性要求）

> 这一节是本项目的**执行纪律**，不是建议。每一阶段收尾时必须逐条完成，否则视为该阶段未结束。

### 9.1 阶段收尾检查清单（Definition of Done）

| # | 动作 | 目标文件 |
| --- | --- | --- |
| 1 | 新建或追加**本阶段的落地记录**：做了什么、关键决策、踩坑与解法、验证结果、遗留问题 | `docs/devlog/Mx-*.md` |
| 2 | 更新**总落地文档**：进度表、已完成能力清单、变更历史追加一条 | `docs/implementation-status.md` |
| 3 | 更新**本文**：勾选已完成任务（⬜ → ✅）、阶段状态改为完成、补上"实际耗时"与"风险实际发生情况" | `docs/development-plan.md`（本文） |
| 4 | **若实现偏离了技术方案**，更新方案对应章节并升版本号（v1.x → v1.x+1），在变更说明里写清"为什么偏离" | `docs/personal-blog-tech-plan.md` |
| 5 | 追加**工作记忆**：记录本阶段的可复用结论与约定 | `.workbuddy/memory/YYYY-MM-DD.md` |

### 9.2 更新原则

- **不删历史**：任务状态是勾选（⬜ → ✅），不是删除。变更历史是**追加**，不是覆盖。
- **记录偏离，而不是粉饰**：如果实现与方案不一致，改方案文档并把原因写清楚。方案文档的价值在于它是"当时的决策依据"，藏着不改会让后续所有判断都建立在错误前提上。
- **踩坑必须落文档**：同一个坑踩两次是纯浪费。踩坑记录写进 `docs/devlog/`，并在技术方案对应章节加一行"⚠️ 已踩"标注。
- **总落地文档是唯一入口**：想知道"现在项目到哪了"，只看 `docs/implementation-status.md` 一个文件就够，不需要翻其他文档。

### 9.3 文档版本约定

| 变更类型 | 版本号 |
| --- | --- |
| 选型/架构变化、新增或删除阶段 | 次版本号 +1（v1.0 → v1.1） |

## 10. 跨阶段的通用约束
